# What the Paho interoperability suite fails against this broker, and why.
#
# The runner compares the tests that fail against this list and fails the
# build on any difference in either direction: a test that starts failing
# is a regression, and a test listed here that starts passing means the
# line is stale and must be removed. The suite has no expected-failure
# mechanism of its own, so the comparison lives in `run.sh`.
#
# Every line is classified as one of:
#
#   deferred   a later milestone covers it; nothing is wrong today
#   assumption the suite asserts something the specification permits
#              rather than requires, or the suite's own client is at
#              fault
#   defect     a real defect in this broker, reported and not yet fixed
#   flaky      the test's own race; its result is ignored in both
#              directions, because listing it as failing would break the
#              build on the runs where it passes
#
# Format: <suite>:<test> <classification> <one line>

# --- the suite assumes more than the specification requires ------------
# Half true since the keep-alive ceiling landed: the broker does send
# Server Keep Alive, whenever an operator has configured a maximum
# below what the client proposed. Here nothing is imposed, because the
# suite proposes 120 and the runner uses the shipped default of 3600,
# which is deliberate: a conformance run tests the defaults. So this
# is not a feature we declined to build, and it does not need
# investigating again.
v5:test_server_keep_alive    assumption 3.2.2.3.14 says the Server MAY send Server Keep Alive; the test asserts it is present, and hard-codes 60.
v5:test_server_topic_alias   assumption 3.3.2.3.4 lets a Server use topic aliases; the test asserts it does.
v5:test_flow_control2        assumption The broker does send DISCONNECT 0x93 after 1024 unacknowledged QoS 2 publications; the suite's client raises BrokenPipeError writing the next PUBREL before it reads the DISCONNECT already in its buffer.
v5:test_subscribe_failure    assumption The subscription to test/nosubscribe is refused, with 0x87 Not authorized, which 3.9.3 lists for SUBACK; the test asserts 0x80, the one failure code 3.1.1 has. The 3.1.1 pass of the same test passes.

# --- the test races with itself ----------------------------------------
v5:test_subscribe_options    flaky      Waits on aclient's subscribeds after bclient subscribes, so it can publish before bclient's SUBSCRIBE is processed; observed passing three runs in four, and a direct probe shows noLocal routing is correct.

# --- the same suites through TLS and WebSocket ---------------------------
# `via.py` carries the suite's plain client through each layer, so what
# fails is what fails above, under the label of the layer. A line here
# that the plain pass does not have would be a defect in the layer, and
# is fixed there rather than classified.
v5-tls:test_server_keep_alive    assumption As v5.
v5-ws:test_server_keep_alive     assumption As v5.
v5-tls:test_server_topic_alias   assumption As v5.
v5-ws:test_server_topic_alias    assumption As v5.
v5-tls:test_subscribe_failure    assumption As v5.
v5-ws:test_subscribe_failure     assumption As v5.
v5-tls:test_flow_control2        flaky      As v5, but through TLS the race between the client's next PUBREL and the DISCONNECT it has not read yet goes either way: observed passing once in three runs, with the same broker that fails it plain.
v5-ws:test_flow_control2         assumption As v5.
v5-tls:test_subscribe_options    flaky      As v5.
v5-tls:test_request_response    flaky      After bclient subscribes, the test waits on aclient's subscribeds, already met, not bclient's, so the request can be published before bclient's SUBSCRIBE is processed and bclient never sees it: test_subscribe_options's race. Seen failing once through TLS, which adds the latency; the plain and WebSocket runs share the race and have not lost it.
v5-ws:test_subscribe_options     flaky      As v5.
