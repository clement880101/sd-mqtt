# Release Implementation Plan (milestone 7, part 3 of 3)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Milestone 7's exit, met: every section 15 budget measured and met
(idle memory and the 100,000-connection target included), section 10.4's
allocator, the three open questions milestone 7 owns decided and recorded,
a container image, cross-compiled release artifacts, the documentation an
operator installs from, and a published release.

**Architecture:** Nothing in the broker's design changes. The allocator is a
`#[global_allocator]` behind a default feature. Two measurements become
scripts that fail when the budget is missed — idle memory beside
`budgets.sh`, the connection target as a small load generator that is a
workspace member but never shipped. Packaging is a script per artifact and a
Dockerfile, each with a test that inspects what it produced, driven by a
release workflow on a version tag. Decisions are architecture decision
records in a new `docs/decisions/`, which section 17 has always said they
would be.

**Tech Stack:** `mimalloc` (one new direct dependency; 32 of 35 after it),
`cargo-zigbuild` for the Linux musl and macOS cross builds (a build tool,
not a dependency), Docker with `buildx` for a two-architecture image,
GitHub Actions for the release workflow, Python 3 for the measurement and
packaging checks, as the existing scripts are.

**Spec:** `docs/superpowers/specs/2026-09-19-sd-mqtt-design.md`, sections 15
(budgets: idle resident memory under 30 MB, 100,000 concurrent connections
per node on target hardware, the "Today" column), 10.4 (mimalloc on every
non-Windows target, local dynamic TLS on static musl), 16 (milestone 7's exit
criteria: "all budgets met, the full conformance suite green including TLS
and WebSocket, a SCRAM client authenticates and re-authenticates, and a
release is published"; "the container image, cross-compiled release
artifacts and documentation"), 17 (SCRAM iteration default "against
measurements on representative hardware"; channel binding "Milestone 7
decides"; each resolution "recorded as an architecture decision record"),
11.1 (HTTP/2 "revisited when TLS lands"), 3 (notices ship with what ships).

## Global Constraints

- `docs/conventions.md`, all eight plus 7b and 7c. Prove every test can
  fail (4), restore mutations byte-identical with a newer timestamp (7b),
  check free space before calling anything flaky (7c), walk the spec
  sections at the close (8).
- Direct dependencies across broker crates: **under 35** (31 today; this
  plan adds `mimalloc` and nothing else that ships). The load generator is
  a workspace member with `publish = false`, outside the binary; its
  dependencies are already the workspace's (`tokio`, `clap`).
- Release binary, stripped, link-time optimised: **under 15 MB** (9.7 MB on
  macOS arm64 today; measure every artifact, not one).
- Interface bundle, gzipped: **under 150 KB** (67.4 KB).
- Idle resident memory, single node, no clients: **under 30 MB**.
- Concurrent connections per node, target hardware: **100,000**.
- **Every artifact carries `LICENSE`, both `THIRD-PARTY-NOTICES.txt` files
  and the README**, and the notices are the ones generated from that
  artifact's build (section 3). A container image carries them too.
- **Nothing is published without the owner's yes in chat**, per publish: a
  tag pushed, a release created, an image pushed. The workflow may be
  written, tested on a fork-free dry run, and merged before that.
- The conformance baseline changes only with a classified line.
- Secrets never print, in build logs as anywhere else: the release
  workflow takes its registry token from the platform's secret store and
  never echoes it.

## Review Focus

Inputs the spec implies and no task's tests would otherwise exercise, most
likely to bite first. Each has its test in the owning task.

1. **`docker stop` on a running broker.** The container's PID 1 is the
   binary; SIGTERM must reach it and the stop must finish inside Docker's
   ten-second grace with the store flushed, so a durable session survives
   `docker stop && docker start`. (Task 5.)
2. **A container with a read-only root filesystem and a non-root user.** The
   store is a volume the runtime user can write; nothing else is written.
   `docker run --read-only --user 65532 -v data:/data` must come up ready.
   (Task 5.)
3. **An artifact that builds and does not run.** A musl or aarch64 binary
   that links against something absent, or that was built without the
   interface embedded, passes `cargo build`. Each artifact is run — under
   QEMU where the host cannot — and asked for `--version` and for the
   interface page. (Task 6.)
4. **A tag whose number the binary disagrees with.** `v0.7.0` released with
   a binary that says `0.1.0`, or a CHANGELOG section named for another
   version. The release workflow refuses unless the tag, `Cargo.toml`,
   `sdmqtt --version` and the CHANGELOG heading agree. (Task 7.)
5. **Running out of file descriptors under the connection test.** At
   100,000 sockets the limit is the first thing hit. The broker must refuse
   past `max_connections` or `EMFILE` with the backoff it already has —
   counted, not spinning — and the load test must report which limit
   stopped it rather than a bare number. (Task 3.)

## Read first

  measurement here follows — print the number every run, fail when it
  cannot measure, test that it fails.
- `services/broker/crates/server/src/listener.rs` near `EMFILE`: the accept

- `services/broker/crates/sdmqtt/src/main.rs` near `SignalKind::terminate`:
  shutdown on SIGTERM and SIGINT.
- `services/broker/crates/admin/build.rs`: how `services/web/dist` is

- `scripts/rust-notices.py`: notices generated from, and audited against,
  a release binary.
- `.github/workflows/ci.yml`: the jobs a release must also pass.

## Four things settled before you start

**Linux artifacts are static musl.** `x86_64-unknown-linux-musl` and
`aarch64-unknown-linux-musl`, built with `cargo zigbuild`, so one binary
runs on any distribution and the container needs no libc. This is the case
section 10.4 names: musl's allocator would cost a factor of seven, so
mimalloc goes in first and the musl build enables its local dynamic TLS.

**macOS artifacts are built, Windows is not, in this release.** Apple
silicon and Intel macOS are where development happens; Windows has never
been built or tested, and section 10.4 already treats it as the platform
without mimalloc. Shipping an untested Windows binary would be a promise
nobody checked. Recorded as a decision (task 4) so it is revisited, not
forgotten.

**The image is `scratch` plus the binary and its notices.** No shell, no
package manager, nothing to patch. It runs as uid 65532, keeps its store in
`/data`, and configures through `SDMQTT_*` environment variables, which
every setting already has. A health check is the orchestrator's, against
`/health/ready` on the admin port; a `HEALTHCHECK` instruction would need a
client in the image.

**The connection target is measured on Linux, in a container, on this
machine, and the result names the machine.** "Target hardware" is not
defined anywhere; the honest reading is that the measurement says what it
ran on. One process cannot open 100,000 connections to one address and port
from one source address — the ephemeral range is about 28,000 — so the
generator spreads its sockets across source addresses `127.0.0.2` upward.

## Decisions the owner takes before task 7

Asked in chat when the plan is handed over; tasks 1 to 6 do not depend on
them.

- **Where the release is published.** This repository has no remote. The
  workflow is written for GitHub releases and the GitHub container registry
  (`ghcr.io/<owner>/sd-mqtt`); the owner names the repository, or another
  destination.
- **The version number.** The workspace says `0.1.0` and has since
  milestone 1. Proposed: `0.7.0`, the milestone, so a version says what it
  contains; `1.0.0` would claim the stability section 16 does not.

## Tasks

- [x] **Task 1 — mimalloc, per section 10.4.** A `mimalloc` feature on the
  `sdmqtt` crate, on by default, which installs `mimalloc::MiMalloc` as the
  `#[global_allocator]` on every non-Windows target and enables mimalloc's
  `local_dynamic_tls` feature when `target_env = "musl"`. Windows stays on
  the system allocator, as section 10.4 says, though no Windows artifact
  ships (task 4's platform record).
  - Test: `crates/sdmqtt/tests/allocator.rs` starts the binary built with
    the default features and reads `/metrics`; the binary reports its
    allocator in `sdmqtt_build_info{allocator="mimalloc"}`, a gauge at 1
    with the version and allocator as labels (the build-info gauge is new;
    section 11.3's style of a constant series). Built with
    `--no-default-features`, the label says `system`. Mutation: remove the
    `#[global_allocator]` line and the default-features run fails.
  - Measure before and after on this machine with `scripts/mqtt-load.py
    traffic` and record the throughput in the commit message; the spec's
    factor of seven is about musl and is re-measured in task 6.
  - Budgets: dependencies 32, binary size re-measured.

- [x] **Task 2 — idle resident memory, measured and enforced.**
  `scripts/idle-memory.sh` builds nothing; it starts a given release binary
  with a temporary store and default listeners, waits for `/health/ready`,
  waits ten more seconds, reads resident memory (`/proc/<pid>/status`
  `VmRSS` on Linux, `ps -o rss=` on macOS), stops the broker with SIGTERM
  and prints the number against 30 MB with its headroom, failing over it.
  - Test: `scripts/test_idle_memory.sh` points it at a binary that does not
    exist, at one that never becomes ready, and at a fake that reports
    40 MB, and asserts each fails with its own message; the real binary
    passes.
  - CI: a `memory` job on the nightly schedule, as section 15 says.
  - Spec 15: the "Today" column refreshed from `budgets.sh` and this
    script, all five rows, with the platform named, because the column was
    stale again (3.76 MB, 16 dependencies, 52.2 KB against 9.7 MB, 31 and
    67.4 KB).

- [x] **Task 3 — the 100,000-connection target.** A workspace member
  `services/broker/crates/sdmqtt-load` (`publish = false`, a binary the
  release never packages, so `rust-notices.py`'s audit of the shipped
  binary never sees it) that opens N MQTT 3.1.1 connections with a keep-alive, spread
  across source addresses `127.0.0.2..127.0.0.N/30000+2`, holds them for a
  duration while pinging, and prints: connected, refused by CONNACK, failed
  to connect and why (`EADDRNOTAVAIL`, `EMFILE`, timeout), the broker's
  resident memory at the peak, and connections per second.
  - `scripts/connection-target.sh` runs broker and generator in the
    development container with `ulimit -n 1048576` and the broker's
    `max_connections` above the target, and fails unless 100,000 connect
    and stay connected for 60 seconds.
  - Review Focus 5: the same script with `ulimit -n 4096` for the broker
    must end with the broker up, `sdmqtt_sockets_refused_total` counting
    the excess, and broker CPU under one core while refused, read from
    `/proc/<pid>/stat`; the generator's report names `EMFILE` on the broker
    side as what stopped it.
  - Record the result, the machine (CPU, cores, memory, kernel, container
    limits) and the broker's memory per connection in spec 15 and in
    `docs/decisions/0001-connection-target.md`, which creates the
    directory and its `README.md`. If the target is missed,
    the decision record says by how much and why, and the owner decides
    whether to move the budget — section 15's "explicit, recorded decision"
    — before the release.

- [x] **Task 4 — the decisions section 17 and section 11.1 leave to this
  milestone**, each an architecture decision record in `docs/decisions/`
  (made by task 3; its `README.md` says what a record is and lists them),
  and each linked from the spec paragraph it resolves:
  - `0002-scram-iterations.md`: PBKDF2-HMAC-SHA-256 timed at 4,096, 10,000
    and 50,000 rounds by a small bench in the server crate's `scram`
    tests (`#[ignore]`d, run by hand), on this machine and in a container
    limited to a quarter of one core as a stand-in for a constrained
    client, with both tables in the record. The default changes only if
    the numbers argue for it; `auth.scram_iterations` stays configurable.
  - `0003-channel-binding.md`: whether `SCRAM-SHA-256-PLUS` is offered.
    Proposed: not in this release. Deployments that terminate TLS at a
    proxy cannot bind to the client's channel at all, and those that do
    not are rare among MQTT clients; recorded with what would reopen it.
  - `0004-admin-http2.md`: section 11.1 deferred HTTP/2 "until TLS lands".
    TLS landed on MQTT listeners, not the admin listener, which still binds
    loopback by default; HTTP/2 stays off and the one-stream rule stays.
    Recorded with the condition that reopens it: TLS on the admin listener.
  - `0005-platforms.md`: the artifact list, Windows excluded, and why.
  - No code changes unless a record decides one; a changed default gets
    its test, its CHANGELOG line and its README line in the same commit.

- [x] **Task 5 — the container image.** `services/broker/Dockerfile`, multi
  stage: Node 22 builds the interface, a Rust stage with `cargo-zigbuild`
  builds the static musl binary for the target platform, the final stage
  is `scratch` with the binary at `/sdmqtt`, the notices and `LICENSE` in
  `/usr/share/doc/sdmqtt/`, `/data` created and owned by 65532, `USER
  65532`, `EXPOSE 1883 1884`, `ENV SDMQTT_STORAGE_DIRECTORY=/data` and
  `ENV SDMQTT_ADMIN_ADDRESS=0.0.0.0:1884`, `ENTRYPOINT ["/sdmqtt",
  "serve"]`. With the admin listener off loopback the startup refusal
  demands `SDMQTT_ADMIN_TOKEN`, so the image cannot start unguarded.
  - Test: `scripts/test_image.sh` builds the image and asserts, against a
    running container: `/health/ready` answers ready; an MQTT client
    connects (`scripts/mqtt-load.py`); the process is uid 65532; the image
    has no `/bin/sh`; the notices are present; the image is under 25 MB.
  - Review Focus 1: a durable session made through the container survives
    `docker stop` (timed, under ten seconds, exit code 0) and `docker
    start` on the same volume.
  - Review Focus 2: `docker run --read-only` with only `/data` a volume
    comes up ready.
  - `docs` and README: running it, the volume, the ports, every
    environment variable, and that the admin listener inside a container
    must bind `0.0.0.0` and therefore needs `SDMQTT_ADMIN_TOKEN`, which the
    startup refusal already enforces.
  - CI: an `image` job that runs `scripts/test_image.sh` on every push.

- [x] **Task 6 — cross-compiled release artifacts.**
  `scripts/package.sh <target>` builds the interface once, builds `sdmqtt`
  for the target with `--release`, regenerates and audits the Rust notices

  - Test: `scripts/test_package.py` unpacks an archive and asserts the

  - The musl build re-measures section 10.4's claim: `mqtt-load.py
