# Milestone 1.5: Spec Gaps Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close what a walk of the design against the code found, so that
milestone one delivers what section 5 and section 6 of the spec say it does.

**Architecture:** Four real defects, five features that exist but have no test
that could fail, and a set of spec sentences that describe something other
than what was built. The defects are in the connection shell, the session
window and the shared-subscription selector. Nothing here is a redesign.

**Tech Stack:** Rust, `tokio`, the project's own `mqtt-codec` and `broker-core`.

---

## Where this came from

Convention 8 says to walk a milestone's spec sections and name the task that
implements each line before the milestone closes. That walk was done. The
conformance suite had already found eight defects; the walk found ten more
things, none of which a conformance suite can see, because a broker that
always supports quality of service 2 and always accepts a retained message is
a legal broker whatever it advertises about itself.

**Read the audit's reasoning in section 17 of the design spec before you
start.** Every finding below was reached by reading the code path, not by
grepping for a name and finding nothing.

## Conventions

`docs/conventions.md`, all eight, and especially:

- **Mutation testing is not optional.** Sixteen mutations were made by hand
  against the previous eight fixes and eight survived. The two shapes that
  recur are a test that asserts around a boundary rather than on it, and a
  test that reaches the easy half of a rule.
- **`cp` backups, not `git checkout --`.** The working directory is shared
  with a live session.
- **The plan's code is a sketch of intent, not a compiling API.** Adapt to
  the real signatures and say what you changed.

From `services/broker`, before every commit:

```bash
cargo fmt --all --check && cargo clippy --all-targets -- -D warnings && cargo test --workspace && ./conformance/run.sh
```

The conformance baseline must not change. If a task makes a listed test pass,
that is a finding: say so, because it means the classification was wrong.

### Task 1: The inflight window is the lesser of ours and the peer's

**Files:**
- Modify: `crates/broker-core/src/broker/mod.rs` (`BrokerConfig`)
- Modify: `crates/broker-core/src/session/state.rs` (`Session::new`)
- Modify: `crates/server/src/connection.rs` around line 228
- Modify: `crates/sdmqtt/src/config.rs`

Section 6 says the inflight window is "the lesser of the configured maximum
and the peer's receive maximum", defaulting to 20.

Neither half is true. `Session::new` hardcodes 20, and the shell then
**assigns** the peer's receive maximum over it rather than taking a minimum.
A version 5 client that advertises nothing is given 65,535, because that is
what an absent Receive Maximum means. There is no configured maximum
anywhere: the 20 is a literal.

So the broker will hold up to 65,535 unacknowledged messages per session
against a default it documents as 20, and an operator has no way to say
otherwise. The queue's byte budget still bounds total memory, so this is not
a leak; it is the wrong number, undocumented, and unreachable.

**A window of 1 must be reachable from configuration**, because section 6
says that is how strict ordering is asked for, and today it can only be had
by a client advertising a Receive Maximum of 1.

- [ ] **Step 1: Write the failing tests**

Three, because three different things are wrong:

```rust
#[tokio::test]
async fn a_client_that_advertises_no_receive_maximum_gets_the_configured_window() {
    // An absent Receive Maximum means 65535, which is not a licence to
    // hold 65535 messages: section 6 takes the lesser of the two.
}

#[tokio::test]
async fn a_client_that_advertises_more_than_we_allow_gets_our_number() { }

#[tokio::test]
async fn a_client_that_advertises_less_than_we_allow_gets_its_own_number() { }
```

The second and third are the two sides of the minimum. A test of only one
passes against code that always takes ours, or always takes theirs.

Drive them through a real connection, not through `set_inflight_limit`: the
defect is in the wiring, and a unit test of the setter already passes.

- [ ] **Step 2: Run them and watch the first two fail**

- [ ] **Step 3: Add the configured maximum**

`BrokerConfig` gains `max_inflight: u16`, default 20, and `Session::new`
takes it rather than the literal. Add a `max_inflight` key to the TOML
config with the same default.

- [ ] **Step 4: Take the minimum in the shell**

```rust
// Section 6: the lesser of the two. An absent Receive Maximum means
// 65535 [3.1.2.11.3], so assigning the peer's value would quietly
// replace the configured window with the protocol's ceiling.
session.outbound.set_inflight_limit(window.min(configured));
```

Apply it for 3.1.1 as well, which advertises nothing and must therefore get
the configured maximum rather than today's accidental 20.

- [ ] **Step 5: Confirm the tests have teeth**

1. `window.min(configured)` becomes `window`. Tests one and two must fail.
2. It becomes `configured`. Test three must fail.
3. The default changes from 20 to 21. A test must fail; if none does, no
   test pins the documented default, and one should.

- [ ] **Step 6: Commit**

```bash
git commit -m "fix(core): the inflight window is the lesser of ours and the peer's"
```

### Task 2: A rejected protocol version is told so

**Files:**
- Modify: `crates/server/src/connection.rs`, `serve` around line 148 and `first_packet` around line 298
- Test: the same file

Section 2 of the spec says MQTT 3.1 "is rejected with an unacceptable
protocol version response". It is not. `first_packet` propagates the codec's
`UnsupportedVersion` straight out of `serve`, and the socket closes with
nothing written.

Both standards require the CONNACK. MQTT 5 wants reason code 0x84, 3.1.1
wants return code 1, and 3.1.1 requires it even though it then closes
[MQTT-3.1.4-5]. The codec can already encode both; nothing calls it.

The difficulty is that the version is what we could not parse, so there is no
version to encode the reply in. Answer in 3.1.1 form: a client speaking any
version understands a 3.1.1 CONNACK well enough to read the refusal, and a
client we could not parse at all gets nothing, which is all we can do.

- [ ] **Step 1: Write the failing test**

Feed a CONNECT naming protocol level 3, and assert a CONNACK with the
unacceptable-version code arrives before the socket closes. Build the bytes
by hand; the encoder will not produce a version it does not support.

- [ ] **Step 2: Run it and watch it fail**

Expected: the read returns nothing, because the socket closed silently.

- [ ] **Step 3: Answer before closing**

Match `CodecError::UnsupportedVersion` where `first_packet`'s error is
handled, write the refusal, then return the error as now. Use the existing
`refuse` helper if it can be pointed at a version we did not negotiate; say
so in a comment if it cannot and you had to write the bytes directly.

- [ ] **Step 4: Confirm the test has teeth**

1. Delete the write. The test must fail.
2. Send reason `Success` instead. The test must fail, which it will only if
   you asserted the code rather than the arrival of a packet.

- [ ] **Step 5: Commit**

```bash
git commit -m "fix(server): refuse an unsupported version out loud"
```

### Task 3: A shared subscriber whose queue is full is skipped

**Files:**
- Modify: `crates/broker-core/src/subscriptions/shared.rs` and its caller in `crates/broker-core/src/broker/route.rs`
- Test: both

Section 6: "A member whose queue is full is skipped and the next is tried."

`select` advances a cursor and returns a member without reference to queue
depth, so a shared group with one saturated member drops every message that
the rotation hands it. The rest of that paragraph, preferring a local online
member and then the least loaded remote, is deferred to milestone 5 by the
routing-core plan and stays deferred. This clause is not: it needs only the
local queue depth the broker already holds.

The selector cannot see session state, which is why this was missed. Do not
give it access. Instead have the caller ask for a member, and ask again if
that member cannot take the message, up to the size of the group.

Bound the retries by the group size and stop. A group where every member is
full must drop once, not spin.

- [ ] **Step 1: Write the failing test**

A group of two, one member's queue filled to its limit, then a publish.
Assert the other member receives it, and that no drop is reported.

Then a second test: both members full, one drop reported, and the selector
consulted no more than twice.

The second test is what stops the fix becoming a spin. A retry loop with no
bound passes the first test perfectly.

- [ ] **Step 2: Run them and watch the first fail**

- [ ] **Step 3: Implement the retry**

Keep the cursor's advance in the selector. The caller asks, tries, and asks
again on refusal. Make sure a skipped member does not lose its turn in the
rotation in a way that starves it later; say in a comment which you chose.

- [ ] **Step 4: Confirm the tests have teeth**

1. Remove the retry. Test one must fail.
2. Remove the bound. Test two must fail or hang; if it hangs, that is the
   test working, but make it fail cleanly instead.
3. Make the bound the group size plus one. Say what that changes and whether
   any test notices. If none does, the bound is untested.

- [ ] **Step 5: Commit**

```bash
git commit -m "fix(core): a shared subscriber with a full queue is skipped"
```

### Task 4: Server Keep Alive is sent when we impose one

**Files:**
- Modify: `crates/server/src/connection.rs`, `acknowledgement`
- Test: the same file

Section 5.4 lists server keep-alive as in scope for v1, and the property is
never sent. The doc comment on `acknowledgement` says the broker imposes no
keep-alive of its own.

**First establish whether that is true**, because the configuration has a
`max_keep_alive` key. Read what it does today.

- If the broker clamps a client's keep-alive to that maximum without telling
  it, that is a defect and the more serious reading: the client believes it
  may be silent for its own interval, and is disconnected at ours.
  [MQTT-3.2.2-21] says a Server Keep Alive sent in the CONNACK is the value
  the client must use instead of its own.
- If the key is only a rejection threshold, or is unused, then nothing is
  broken and the fix is to send the property when the configured maximum is
  below what the client asked for.

Report which you found. The fix is the same shape either way: when the
configured maximum is lower than the client's proposal, clamp **and** send
`server_keep_alive` so the client knows.

- [ ] **Step 1: Write the failing test**

Connect proposing a keep-alive above the configured maximum. Assert the
CONNACK carries the maximum. Then assert the keep-alive actually enforced
matches what was advertised, which is the half that makes the property
truthful rather than decorative.

- [ ] **Step 2: Run it and watch it fail**

- [ ] **Step 3: Implement**

Pass the negotiated value to `acknowledgement` and set the property only when
it differs from what the client proposed. [MQTT-3.2.2-22]: an absent property
means the client's value stands, so sending it unchanged is noise.

- [ ] **Step 4: Confirm the test has teeth**

1. Send the property always, including when unchanged. A test should catch
   the noise; if none does, add one.
2. Advertise the maximum but enforce the client's proposal. The second
   assertion must fail.

- [ ] **Step 5: Commit**

```bash
git commit -m "fix(server): tell a client the keep-alive we will hold it to"
```

### Task 5: The five rules that work and have no test that could fail

**Files:**
- Test only, across `crates/broker-core` and `crates/server`
- One accessor may be needed; see below

Five behaviours are implemented correctly and guarded by nothing. Each of
these would survive deleting the feature. Write a test for each that fails
when it is deleted, and say in your report which ones you verified by
deleting.

- [ ] **Step 1: An empty retained payload still reaches current subscribers**

The spec calls this out as the easy one to miss: the message is not stored
and not sent to future subscribers, **but it is delivered to the subscribers
matching at the time**. The store half is tested. The delivery half is not,
and no test anywhere in the workspace publishes an empty payload through a
broker.

Subscribe, publish retained and empty, assert the subscriber receives it.
Then connect a second subscriber and assert it receives nothing.

- [ ] **Step 2: The retained expiry sweep actually runs**

`Broker::tick` calls the sweep, and deleting that call changes no test,
because expiry is enforced on read as well. The memory simply never comes
back.

This needs a way to see the store's size from outside. Add a minimal
accessor on `Broker`, used by the test, and say in its doc comment that it
exists for that and what it would otherwise hide.

Retain a message with an expiry, tick past it, and assert the store is empty
**without anyone having read it**.

- [ ] **Step 3: The three CONNECT refusals**

All in `connection.rs`, all untested:

1. A 3.1.1 connect with an empty client identifier and `CleanSession` clear,
   refused with `ClientIdentifierNotValid` [MQTT-3.1.3-8]. Nothing in the
   module sends a 3.1.1 CONNECT at all.
2. A Receive Maximum of zero. Its exact sibling, a Maximum Packet Size of
   zero, is tested. This one matters more: the comment beside it says zero
   would be read as unbounded by the window it feeds, so a silent clamp
   inverts the limit.
3. Every candidate identifier taken, so the connection is refused. The
   helper is tested; the refusal is not.

- [ ] **Step 4: Response Topic and Correlation Data on an ordinary publish**

Guarded only on the will path today. Assert a publisher's response topic and
correlation data reach a subscriber unaltered on a normal publication.

- [ ] **Step 5: The outbound window narrows to the peer's number**

Task 1 may have covered this. Check, and if its tests assert the window
rather than the number of messages that actually go out, add one that counts
what a subscriber receives before it acknowledges.

- [ ] **Step 6: Commit**

```bash
git commit -m "test: guard five rules that no test could fail on"
```

### Task 6: Say what the spec means, or say it is not built

**Files:**
- Modify: `docs/superpowers/specs/2026-09-19-sd-mqtt-design.md`

Six sentences describe something other than what exists. Three are stale
text, three are features nobody built. The rule is the one convention 8
gives: deferred and forgotten look identical in a codebase and opposite in a
review, so each one must say which it is.

- [ ] **Step 1: Correct the three stale descriptions**

1. Section 5.1 says "fourteen MQTT packet types". MQTT 5 has fifteen and the
   code has fifteen, including AUTH.
2. Section 5.1 says properties live in an `Option<Properties>` field. They
   are carried by value. Section 17 already records the boxing question as
   open, so point at it rather than restating the undone design as fact.
3. Section 5.3 describes matching as walking literal, then single-level
   wildcard, then multi-level. The code emits multi-level first. The result
   set is identical and the merge is order-insensitive, so correct the
   sentence rather than the code, and say why the order does not matter.

- [ ] **Step 2: Correct two over-statements**

4. Section 5.2's session-state list includes retain handling per
   subscription. It is not stored, correctly: retain handling only has
   meaning at the instant of subscribing. Say that.
5. Section 5.2's CONNECT order begins with the protocol version "accepted for
   this listener". There is no per-listener version policy; the accepted set
   is in the codec. Either promise the policy for a later milestone or drop
   the phrase. Drop it, and say the accepted set is a property of the build.

- [ ] **Step 3: Rule on the three features that were never built**

Each is legal as it stands, which is why no suite complained. Each needs a
sentence saying it is deliberate.

6. **Maximum QoS** and **Retain Availability**. The broker always supports
   quality of service 2 and always accepts a retained message, and advertises
   neither property. Being able to cap either is an operator policy that
   belongs with authorization. Move both to milestone 7 in section 16 and say
   so in 5.4.
7. **Reason strings on acknowledgements.** The codec can carry one; nothing
   produces one. Section 5.4 already calls them optional. Say that v1 sends
   none, and that the reason code is the contract.
8. **Queue bounds "configured separately for the online and offline cases"
   and per-queue overflow.** One set of bounds exists, hardcoded, and every
   session gets drop-newest. Decide and write down: make the single set
   configurable from TOML in task 7, and drop the online/offline split from
   the spec unless you can say what problem two sets solve. Nobody has
   stated one.

- [ ] **Step 4: Commit**

```bash
git commit -m "docs: say what section 5 and 6 actually promise"
```

### Task 7: The queue bounds reach configuration

**Files:**
- Modify: `crates/broker-core/src/session/queue.rs`, `crates/broker-core/src/broker/mod.rs`, `crates/sdmqtt/src/config.rs`
- Test: `crates/sdmqtt/src/config.rs`

Section 6 calls the queue bounds configured. They are two literals in
`QueueLimits::default`, 1000 messages and 64 MiB, reachable from nothing.
For a broker whose memory budget is a stated goal, the one knob that bounds
per-session memory should be a knob.

Add `max_queue_messages` and `max_queue_bytes` to the TOML config, defaulting
to today's values, and thread them to `Session::new` beside task 1's
`max_inflight`. Overflow stays drop-newest for every session; task 6 decides
whether the spec keeps promising otherwise.

- [ ] **Step 1: Write the failing test**

The config module has a test that every field can be overridden. Extend it,
and add one asserting the defaults are unchanged from the literals they
replace, so that moving them cannot quietly change them.

- [ ] **Step 2: Implement and confirm**

Mutation: change a default. The defaults test must fail.

- [ ] **Step 3: Commit**

```bash
git commit -m "feat(config): the queue bounds are configurable"
```
