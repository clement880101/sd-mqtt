# Interface Pages Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Milestone three's exit criterion: the interface shows live clients
and retained messages against a running broker.

**Architecture:** Three pages over the admin API. One events stream for the
whole application, not one per page, because a browser allows six
connections to an origin and an always-open stream holds one.

**Tech Stack:** Preact 10 with signals, uPlot for charts,
`@tanstack/virtual-core` for the client table, valibot for the publish form.

## What is already settled

**One events stream for the application.** Open it once, above the routes,
and let pages read from it. Three pages each opening their own would use
three of the browser's six connections to the origin.

**A reconnect is not automatic correctness.** The server replays from a ring
and sends a resynchronise event when a reader has fallen too far behind. The
interface must handle that event by refetching, not ignore it. A stream that
silently misses events looks fine and is wrong, which is the whole reason the
server does this work.

**The bundle budget is 150 KB gzipped and the shell uses 13.3 KB.** uPlot is
about 23 KB, the virtual core about 7, valibot about 2. There is room; there
is not room to be careless.

## Conventions

Branch is `feat/api`. The Rust gates still apply if you touch Rust:

```bash
cargo fmt --all --check && cargo clippy --all-targets -- -D warnings && cargo test --workspace && cargo deny check && ./scripts/budgets.sh
```

For the interface, the discipline is the same in spirit: for every behaviour
you assert, break the thing and confirm the assertion fails. Say which you
did. Where a page's behaviour can be tested against the real broker rather
than a mock, do that: this project's tests are worth what they touch.

### Task 1: The stream, once, with a reconnect that tells the truth

**Files:**
- Create: `services/web/src/live.ts`
- Modify: `services/web/src/app.tsx`

One module owning the connection and exposing signals the pages read.

It must handle four things, and three of them are easy to forget:

- the connection dropping and coming back, with the browser resending its
  last identifier;
- a resynchronise event, which means refetch the state you hold rather than
  carry on;
- the stream being unavailable at all, which the interface must show rather
  than sit silently empty;
- the retry interval the server sends, which is the server's decision and not
  the browser's default.

- [ ] **Step 1: Write it, then break the server on purpose**

Start the broker, open the interface, then stop the broker. The interface
must say it has lost the connection. Start it again: the interface must
recover without a reload.

Then force a resynchronise by holding the browser tab paused long enough to
fall out of the ring, and confirm the interface refetches rather than showing
stale data forever.

Report what you did and what you saw. These are the behaviours nobody
notices are broken until a demonstration.

- [ ] **Step 2: Commit**

```bash
git commit -m "feat(web): one live connection, and what it does when it breaks"
```

### Task 2: Overview

**Files:**
- Create: `services/web/src/pages/overview.tsx`, `services/web/src/chart.tsx`

Live rate charts from the counter deltas the stream carries, plus the
headline gauges: connections, sessions, subscriptions, retained messages.

uPlot, pinned to the published version. Its repository is much newer than
what is published; depending on a commit is worse for a shipped dependency
because it has no version to audit.

**A rate is a derivative and the stream carries totals.** Compute it from
successive totals with their timestamps, and decide what happens when the
broker restarts and a total goes backwards. A chart that plots a large
negative spike on every restart is the obvious result of not deciding.

- [ ] **Step 1: Build it against a running broker, with real traffic**

Publish a steady stream of messages from a client and confirm the chart shows
it. A chart that draws nothing convincingly is the failure mode here.

- [ ] **Step 2: Handle the counter going backwards, and say what you chose**

- [ ] **Step 3: Commit**

```bash
git commit -m "feat(web): the overview page"
```

### Task 3: Clients

**Files:**
- Create: `services/web/src/pages/clients.tsx`

A filterable table, windowed with the virtual core, over the clients
resource. This is half the exit criterion.

The resource paginates. A windowed table over a paginated resource has to
decide what it does when the window reaches the end of what it has fetched,
and the honest answers are to fetch more or to say there are more. Pick one
and make it visible; a table that silently shows the first page as though it
were everything is a lie about the broker's state.

- [ ] **Step 1: Write it, and test it against a broker with many clients**

Connect several hundred clients and confirm the table stays responsive and
shows them. A virtualized table tested with five rows is not tested.

- [ ] **Step 2: Live updates**

A client connecting or disconnecting must appear or disappear without a
reload, which is what the stream is for.

- [ ] **Step 3: Commit**

```bash
git commit -m "feat(web): the clients page"
```

### Task 4: Topics

**Files:**
- Create: `services/web/src/pages/topics.tsx`

A retained browser, and a publish and subscribe tool. The other half of the
exit criterion.

The publish form validates with valibot before sending. Validate what the API
will reject: an empty topic, wildcards in a topic name, a quality of service
outside its range. Better to say so in the form than to round-trip an error.

The subscribe half needs live messages, which the events stream does not
carry: it carries counter deltas and connection events, not publications.
**Decide how the tool receives messages and write down why.** Extending the
events stream to carry publications for a subscribed filter is one answer and
has an obvious abuse: a filter of `#` on a busy broker. Whatever you choose,
the limit that stops that has to exist.

- [ ] **Step 1: Decide the subscribe mechanism before building it**

Write the decision and its limit into the plan's own notes or the readme, and
say what it costs.

- [ ] **Step 2: Build the retained browser**

Retain messages on several topics, confirm they are listed, confirm clearing
one with an empty payload removes it from the list.

- [ ] **Step 3: Build the publish and subscribe tool**

- [ ] **Step 4: Commit**

```bash
git commit -m "feat(web): the topics page"
```
