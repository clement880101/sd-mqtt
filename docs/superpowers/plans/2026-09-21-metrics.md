# Metrics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every counter and gauge section 11.3 names, rendered in the
Prometheus text format, with nothing discarded anywhere in the broker that is
not counted. And the budgets section 15 claims are enforced actually enforced.

**Architecture:** One `metrics` module in the server crate holding a registry
and a flat set of pre-resolved handles. `broker-core` stays pure and counts
nothing: it already reports every drop as an action with a reason, and the
shell counts what it sees.

**Tech Stack:** `prometheus-client` 0.25.

## Two things that decide the shape

**Resolve every label combination at startup.** A metric family is a
read-write-locked map, and the obvious update call holds the guard across the
increment. Incrementing on the packet path would therefore put a shared lock
acquisition on every packet, on every worker thread. The counter behind a
family is an atomic behind a reference count, so taking an owned handle once
makes the increment a bare atomic add. The label cross-product here is
bounded and static: packet types by version, drop reasons, socket outcomes.
Resolve them all into a flat array at startup and never touch the family
again.

This is not an optimisation to consider. This project rejected a timer
design for exactly this pathology and measured a lock costing it 75% of its
throughput.

**Do not mirror what already exists.** Queue depth, session count,
subscription count and retained-message count live in authoritative
structures the broker already owns. A gauge holding a second copy is two
sources of truth and a drift bug. Register a collector that reads the live
value when the endpoint is scraped instead. Counters are real counters;
derived gauges are read at scrape time.

### Task 1: The registry and its handles

**Files:**
- Create: `crates/server/src/metrics.rs`
- Modify: `crates/server/src/lib.rs`, `crates/server/Cargo.toml`

- [ ] **Step 1: Add the dependency and confirm the gate**

`prometheus-client = "0.25"`, default features, which are empty. Then
`cargo deny check` must pass with `deny.toml` unchanged. If anything is
rejected, stop and report rather than editing the allow list.

- [ ] **Step 2: Write the failing test**

A registry renders a counter that has been incremented, with the exact
expected text. Assert the whole rendered block, not that it contains a
substring: the format is what a scraper parses, and a test that accepts any
text containing a name would pass against a malformed exposition.

- [ ] **Step 3: Build the registry and the handles**

A `Metrics` struct holding the registry and every resolved handle. Handles
indexed by discriminant, not looked up by label.

Label values must be lower case. The derive takes enum variant names
verbatim, which gives `Publish` where Prometheus convention wants `publish`,
so write the label-value implementation by hand rather than deriving it.

- [ ] **Step 4: Confirm it has teeth**

1. Change a metric's name. The exposition test must fail.
2. Change a label value's case. The same test must fail, which it will only
   if it asserts the text rather than the presence of a name.

- [ ] **Step 5: Commit**

```bash
git commit -m "feat(server): the metric registry and its handles"
```

### Task 2: Counters for what happens on a connection

**Files:**
- Modify: `crates/server/src/metrics.rs`, `connection.rs`, `listener.rs`, `shared.rs`
- Test: those files

Section 11.3's list, the parts a connection sees: packets by type, version and
reason code; socket lifecycle; bytes in and out; authentication outcomes.

Authentication does not exist until milestone 7. Register the counter with no
outcomes recorded and say in a comment that it is deliberately zero rather
than missing, so that a scraper's dashboard does not need changing later.

- [ ] **Step 1: Write the failing tests**

Drive a connection through the existing test harness and assert the counters
moved: a connect and a publish counted by type and version, bytes counted in
both directions, a socket opened and closed counted once each.

Count bytes where they are read and written, not by adding up what packets
should have been. The point of a byte counter is to catch the difference.

- [ ] **Step 2: Implement, run, and confirm teeth**

Mutations: count a publish as a connect; count bytes on the read side only;
increment the socket gauge without ever decrementing it. Each must fail a
test. The third is the one that matters, because a gauge that only rises
looks right for an hour.

- [ ] **Step 3: Commit**

```bash
git commit -m "feat(server): count what happens on a connection"
```

### Task 3: Nothing is discarded without being counted

**Files:**
- Modify: `crates/server/src/metrics.rs`, `shared.rs`, `connection.rs`
- Test: those files

Section 11.3: "Every discard path has both a metric and a hook. A message
never disappears without being counted."

Hooks are milestone 4. The metric is now, and the harder half is
**exhaustiveness**, which is the same problem the journal had.

The discard paths that exist today. Find them rather than trusting this list,
and report any you find that is not on it:

- the seven queue drop reasons reported as an action with a reason
- a full outbox, which the shell already counts
- a batch the storage writer refused
- an oversize packet discarded before it is written

- [ ] **Step 1: Write the exhaustiveness test**

Not a list of assertions. The drop reasons are an enum, so write a test that
walks every variant and asserts each has a distinct counter that moves. A new
variant added later must fail to compile or fail this test.

Say in the report which mechanism you used, because "fails to compile" is
much better than "fails at run time" and is usually available with an
exhaustive match.

- [ ] **Step 2: Implement, run, confirm teeth**

Mutations: map two drop reasons to one counter; drop the slow-reader count.

- [ ] **Step 3: Commit**

```bash
git commit -m "feat(server): every discard is counted"
```

### Task 4: Gauges that read the truth rather than copy it

**Files:**
- Modify: `crates/server/src/metrics.rs`
- Test: the same file

Connections, sessions, subscriptions, retained messages and queue depth.
Registered as a collector that reads the authoritative structure at scrape
time. Cluster members are milestone 5 and are not registered at all; say so
in a comment.

Queue depth across all sessions may be expensive to compute by walking every
session. Find out what it costs before you write it that way. If it is
expensive, say so and report the total the broker already maintains, or add
a maintained total, but do not put a walk of every session behind an endpoint
a scraper hits every fifteen seconds.

- [ ] **Step 1: Write the failing test**

Create sessions and subscriptions, scrape, and assert the numbers. Then
remove one and scrape again. The second half is what catches a gauge that
only ever rises.

- [ ] **Step 2: Implement, run, confirm teeth**

Mutations: report the count at registration time rather than at scrape time;
count sessions where subscriptions were meant.

- [ ] **Step 3: Commit**

```bash
git commit -m "feat(server): gauges read from the structures that hold the truth"
```

### Task 5: The budgets section 15 claims are checked

**Files:**
- Create: `scripts/budgets.sh`
- Modify: `.github/workflows/ci.yml`

Section 15 says budgets are checked in CI and that exceeding one fails the
build. That has never been true. Two shipped milestones went by without it,
which convention 8's walk found.

Three are cheap and start now:

| Budget | Target | How |
|---|---|---|
| Release binary, stripped | under 15 MB | build with the release profile and measure the file |
| Direct dependencies across broker crates | under 35 | count distinct direct dependencies in the workspace manifests |
| Interface bundle, gzipped | under 150 KB | skipped while no interface exists; the script must say so out loud rather than passing silently |

Idle resident memory is measurable but needs a process started and settled,
so it is a scheduled job rather than a gate on every push. The connection
target is a load test and is milestone 7's.

**A budget check that silently passes when it cannot measure is worse than no
check.** The bundle line must report that it was skipped and why.

- [ ] **Step 1: Write the script, and make it fail first**

Set a budget deliberately low, confirm the script exits non-zero and names
which budget and by how much. Then set the real figures.

- [ ] **Step 2: Report the numbers even when they pass**

A budget at 94% and a budget at 4% are different situations and a green tick
hides which one you are in. Print each budget, its measurement and the
headroom.

- [ ] **Step 3: Wire it into CI and record today's figures**

Add the job. Put the current binary size and dependency count into section 15
beside the targets, so the next person can see the trend rather than only the
limit.

- [ ] **Step 4: Commit**

```bash
git commit -m "ci: check the budgets section 15 said were checked"
```
