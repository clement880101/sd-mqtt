# Cluster Routing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A message published on one node reaches a subscriber on another,
one copy per interested node, with shared subscriptions delivered once across
the cluster rather than once per node.

**Architecture:** Each node holds the full subscription trie for its own
clients plus a map from filter to the remote nodes that have a matching
subscriber, which the replicated metadata already carries. A publish matches
locally, enqueues locally, and forwards one copy to each interested node. A
forwarded message is marked and is never forwarded again.

**Tech Stack:** The `cluster` crate's link and metadata, `broker-core`'s
matching layer.

## Three things settled before you start

**Shared subscriptions cannot use the routing map, and this is the trap the
whole plan is arranged around.** A group spanning three nodes has a matching
subscriber on each, so forwarding one copy to each interested node delivers
three times where the semantics demand one. They need a separate map from
group to member nodes and a selection *before* forwarding rather than after.

**A forwarded message is marked and never forwarded again.** Stated as an
implication in the original design, which is the difference between a mesh
and an infinite loop. The same mark decides where a rule fires: on the node
where the message entered the cluster, which is the node that received it
unmarked.

**Section 6's remote ordering waits.** Preferring a local member is
implementable now. Preferring the least loaded remote node needs a queue
depth from another node, which arrives with queue replication in milestone 6.
Implement the local preference, and say in the code that the remote ordering
is deferred rather than forgotten.

### Task 1: Who else wants this filter

**Files:**
- Create: `crates/cluster/src/routes.rs`
- Modify: `crates/cluster/src/metadata.rs`
- Test: those files

A map from filter to the set of remote nodes with a matching subscriber,
built from the registers metadata replication already carries, and kept
current as they arrive and are tombstoned.

**Matching a topic against remote filters is the same problem the local trie
solves**, and the trie is in another crate that must not depend on this one.
Decide: reuse the trie by giving it a second instance keyed by node, or match
remote filters some other way. Say what you chose and what it costs, because
a linear scan over every remote filter per publish is the obvious wrong
answer and the design's own ceiling is fifty nodes.

- [ ] **Step 1: Write the failing tests**

A register arriving adds its node for that filter. A tombstone removes it. A
node going dead removes all of its filters, which is a case no register
covers because nothing was written. Two nodes subscribing to one filter are
both returned. A topic matching a wildcard filter returns its node.

The dead-node case is the one to be careful about: membership is not
replicated, so it is a local judgement, and a node that is dead must stop
receiving forwards without anything having been written down.

- [ ] **Step 2: Implement, confirm teeth, commit**

Mutations: a tombstone not removing the node; a dead node still returned; a
wildcard filter matched as a literal.

```bash
git commit -m "feat(cluster): which nodes want a topic"
```

### Task 2: Forwarding

**Files:**
- Create: `crates/cluster/src/forward.rs`
- Modify: `crates/server/src/publish.rs`, `crates/broker-core/src/broker/mod.rs`
- Test: those files

A publish matches locally, enqueues to local sessions, and forwards one copy
to each interested remote node. A node receiving a forward matches it against
its own local subscribers only.

**The mark is the whole of the loop prevention.** Write the test that a
forwarded message is not forwarded on, and write it with three nodes where
the middle one has a subscriber, because two nodes cannot tell a mesh from a
line.

- [ ] **Step 1: Write the failing tests**

A publication on one node reaches a subscriber on another. A publication
reaching a node with no subscriber for it is not forwarded there at all,
which is the economy the design is built on and which a test asserting
delivery cannot see. A forwarded message is not forwarded again. A rule fires
on the node where the message entered and not on the node that received the
forward.

- [ ] **Step 2: The third deferred metric**

The router-match split, local and remote, which milestone 3 deferred to here
and recorded as deferred. Add it, and remove the deferral note.

- [ ] **Step 3: Implement, confirm teeth, commit**

Mutations: the mark not set; the mark not checked; a forward sent to every
node rather than the interested ones; the rule fired on a forward.

The second and third are the pair that each alone looks correct.

```bash
git commit -m "feat(cluster): one copy to each node that wants it"
```

### Task 3: A shared group is delivered once

**Files:**
- Create: `crates/cluster/src/groups.rs`
- Modify: `crates/cluster/src/forward.rs`, `crates/broker-core/src/subscriptions/shared.rs`
- Test: those files

The trap. A group spanning three nodes must receive one message, not three.

A separate map from group to the nodes with a member, and a selection before
forwarding: choose one node, forward only there, and let that node choose
among its own members. Prefer a local member when this node has one, because
that saves a hop and a network copy.

- [ ] **Step 1: Write the failing test first, and watch it fail**

Three nodes, one shared group with a member on each, one publication. Exactly
one delivery. Run it before you write anything: it must fail with three,
because that is what the routing map alone does, and seeing the three is what
makes the rest of the task make sense.

- [ ] **Step 2: Then the distribution**

Over many publications every member node is chosen, which is what makes it a
shared subscription rather than a fixed route. A local member is preferred
when there is one.

An ordinary subscription and a shared one matching the same topic both
deliver, which is a case the group map can easily swallow.

- [ ] **Step 3: Implement, confirm teeth, commit**

Mutations: the group map ignored and the ordinary path used, which the
one-delivery test must catch; the local preference dropped; one node always
chosen.

```bash
git commit -m "feat(cluster): a shared group is delivered once, not once per node"
```
