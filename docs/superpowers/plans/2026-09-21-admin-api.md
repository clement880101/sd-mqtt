# Admin API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An admin listener serving health, metrics, the read resources the
first three interface pages need, a publish endpoint, and an events stream a
browser can reconnect to without losing anything silently.

**Architecture:** A new `admin` crate holding an axum router over the same
`Shared` the MQTT listener uses. It reads the broker under the existing lock
and writes through the same path a connection does, so there is no second set
of rules. The events stream is fed by a bounded ring of recent events, which
is what makes a reconnect honest.

**Tech Stack:** `axum` 0.8 with minimal features, `serde_json`, the
`prometheus-client` registry built in the previous plan.

## Four things that are not negotiable

**The stream must end when the broker stops.** Graceful shutdown waits for
every open connection and an events body never ends on its own, so one
browser tab left open would stop the broker exiting. A clean stop is how
sessions reach disk, so this is a data bug wearing a usability costume. Each
stream selects on the shutdown signal, and the server is bounded by a timeout
as a backstop.

**A dropped event must be counted and must be visible to the browser.** A
broadcast channel drops for a slow receiver and reports it as an error the
usual combinator throws away. Section 11.3 forbids a message disappearing
uncounted. A reader that has fallen behind gets a resynchronise event telling
it to refetch, not a quiet gap.

**Binding a non-loopback address with no token is refused at startup.** Not
warned about. The endpoints include publishing. The refusal names the address
and the missing key.

**Never compress the events stream, and tell intermediaries not to buffer
it.** A compression layer applied across the listener turns a live stream
into batch delivery, which presents as an interface that updates in clumps
and is miserable to diagnose.

### Task 1: The crate, the listener, and refusing to be unsafe

**Files:**
- Create: `crates/admin/Cargo.toml`, `crates/admin/src/lib.rs`, `crates/admin/src/config.rs`
- Modify: `crates/sdmqtt/src/config.rs`, `crates/sdmqtt/src/main.rs`

`axum` with default features off and `http1`, `tokio`, `json`, `query`,
`matched-path` and `tracing`. The defaults cost only two crates, so the
reason to turn them off is not weight: the form extractor widens the surface
of a JSON-only API, and the tower logging feature routes internals through a
second logging facade beside the tracing this project standardised on.

There is no feature for the events stream; it is unconditional.

Configuration: the admin address, defaulting to a loopback address and a
port, and an optional token. Starting the admin listener is not optional, but
an operator may disable it.

- [ ] **Step 1: Write the failing tests**

Binding a non-loopback address with no token fails to start, with an error
naming the address and saying a token is needed. The same address with a
token starts. A loopback address with no token starts.

Three tests, because the rule has three cases and a test of one passes
against a guard that refuses everything or nothing.

- [ ] **Step 2: Implement, run, confirm teeth**

Mutations: accept a non-loopback address with no token; refuse loopback too.
Check what your guard does with a wildcard address, which is neither loopback
nor a specific interface, and make sure the answer is deliberate.

- [ ] **Step 3: Commit**

```bash
git commit -m "feat(admin): the listener, and what it refuses to be"
```

Section 11.1: liveness answers whether the process is running; readiness
answers whether listeners are bound and storage is open; a cluster endpoint
answers whether membership is complete.

Cluster membership is milestone 5. Serve the endpoint and have it answer that
this node is a cluster of one, rather than leaving the path absent, so an
operator's configuration does not have to change later. Say so in a comment.

The metrics endpoint renders the registry from the previous plan, with the
content type the exposition format requires.

- [ ] **Step 1: Write the failing tests**

Liveness answers before listeners are bound. Readiness does not: it answers
unready while storage is not open, and ready once it is. That difference is
the whole point of two endpoints, and a test that only checks both return a

Metrics returns the exposition text with the right content type.

- [ ] **Step 2: Implement, run, confirm teeth**

### Task 3: The read resources

**Files:**
- Create: `crates/admin/src/resources.rs`
- Test: the same file

The resources the first three pages need: nodes, listeners, clients,
sessions, subscriptions and retained messages. Rules, dead letters, users,
access control and API keys are later milestones and are not served at all.

Read through the same lock everything else uses, and hold it for the shortest
possible span. **A request that lists a hundred thousand sessions must not
hold the process lock while serialising them.** Take what you need under the
lock, release it, then serialise. Say in a comment that this was the reason
for the shape, because the obvious code does the opposite.

Paginate anything that can be large. A client list is the page that motivated
a virtualized table, so it will be large by design.

- [ ] **Step 1: Write the failing tests**

Each resource returns what the broker actually holds: connect a client,
subscribe, retain a message, and assert each appears. Then disconnect and
assert it stops appearing.

The second half matters. A list that only ever grows looks right until
someone leaves.

- [ ] **Step 2: Decide the error shape and write it down**

Section 13 governs. One shape for every error the API returns, including a
code a client can branch on rather than a human sentence it would have to
match. Write it once, use it everywhere, and test that an unknown resource
and a malformed request both produce it.

- [ ] **Step 3: Implement, run, confirm teeth**

Mutations: serialise under the lock, and confirm your comment is testable or
say it is not; report a disconnected client as connected; return an empty
page rather than the last page at a boundary.

- [ ] **Step 4: Commit**

```bash
git commit -m "feat(admin): the resources the first pages need"
```

### Task 4: Publishing

**Files:**
- Modify: `crates/admin/src/resources.rs`
- Test: the same file

A publish endpoint, which is the first mutating endpoint and therefore the
first that needs the token when one is configured.

**It must go through the same path a connection does.** A second publish
implementation in the admin crate would be a second set of rules about
retention, expiry, matching and queueing, and the two would drift. Find how a
connection publishes and use it.

An at-least-once publish through the API must wait for durability exactly as
one over MQTT does, for the same reason: the response is a promise.

- [ ] **Step 1: Write the failing tests**

A publish reaches a subscriber connected over MQTT. That is the test that
proves it went through the real path rather than a parallel one.

Without a token, when a token is configured, it is refused. With the wrong
token, refused. With the right one, accepted.

An at-least-once publish does not answer until it is durable, proved with a
held flush exactly as the connection's test does.

- [ ] **Step 2: Implement, run, confirm teeth**

Mutations: skip the token check; compare tokens with an ordinary equality
that returns early, and say whether that matters here and why; answer before
durability.

On the second: a timing-safe comparison for a secret is the habit worth
having even where the threat is remote. Decide, and write down which you
chose and why.

- [ ] **Step 3: Commit**

```bash
git commit -m "feat(admin): publishing, through the path that already exists"
```

### Task 5: The events stream and its ring

**Files:**
- Create: `crates/admin/src/events.rs`
- Test: the same file

The hardest task here, and the one with the most ways to look finished while
being wrong.

The ring holds recent events keyed by a monotonic identifier. A subscriber
gets the backlog from its requested identifier, then the live feed. A
requested identifier older than the ring holds gets a resynchronise event
instead of a gap.

Events: counter deltas, connect and disconnect. Rule outcomes are milestone 4.

- [ ] **Step 1: Write the failing tests**

- A reconnect with a last-event header receives exactly the events it missed,
  once each, in order.
- A reconnect asking for an identifier older than the ring receives a
  resynchronise event and no gap pretending to be complete.
- A subscriber that falls behind the live channel is counted, and receives
  the resynchronise rather than silently missing events.
- The stream ends when the shutdown signal fires. Prove it by asserting the
  server task finishes, not by asserting the stream produced something.
- Identifiers are monotonic across a reconnect.

The third is the one most likely to be missing, and it is the one the whole
ring exists for.

- [ ] **Step 2: Implement**

Set the retry interval the server sends, rather than leaving the browser's
default: a broker that has just restarted does not want every browser
retrying every three seconds.

Set the header that tells intermediaries not to buffer, and make sure no
compression applies to this route.

- [ ] **Step 3: Confirm it has teeth**

Mutations: discard the lag error rather than turning it into a
resynchronise; serve the backlog from the ring's start rather than from the
requested identifier; never end the stream on shutdown, and confirm a test
fails rather than hanging; emit identifiers that restart at one per
connection.

The fourth mutation is worth care. A test that hangs is a test that failed,
but it is a bad failure: make the shutdown test time out and fail cleanly.

- [ ] **Step 4: Commit**

```bash
git commit -m "feat(admin): an events stream a reconnect can trust"
```

### Task 6: It comes up with the broker, and goes down with it

**Files:**
- Modify: `crates/sdmqtt/src/main.rs`
- Test: `crates/sdmqtt/tests/`

The admin listener starts after restore and beside the MQTT listener, and
both stop on the same signal.

- [ ] **Step 1: Write the failing test**

Start the real binary, fetch the health endpoint and the metrics endpoint
over a real socket, then send the termination signal and assert the process
exits zero **with a browser still holding an events stream open**.

That last clause is the test. Without it this passes against the shutdown bug
the design warns about, and that bug costs every session that had not
reached disk.

- [ ] **Step 2: Implement, run, confirm teeth**

Mutation: remove the stream's shutdown arm and confirm the test fails rather
than hanging forever. Give the test a timeout so it reports rather than
stalls a build.

- [ ] **Step 3: Commit**

```bash
git commit -m "feat(sdmqtt): serve the admin listener beside the broker"
```
